# 推理模型「思考过程」（思维链）支持方案

> **建立日期**: 2026-09-18
> **来源**: `docs/62_专家团最终审核报告.md` —— P1-2 指出「推理通道 `reasoning_content` 未解析」
> **当前状态**: ✅ 已完成并发布 **v0.6.31** —— 全链路打通（适配器 → 引擎 → 服务端 WS → 前端 UI），
> 新增 8 条模块测试，全量回归 **1680/1680**

---

## 一、问题

推理模型（DeepSeek-R1 / Qwen3-thinking / GLM-Z1 / OpenAI o 系列等）会**先输出一长串思维链，
再输出正式回答**。原实现只认 `content` / `delta.content`，推理字段完全没接，导致两种糟糕体验：

| 处理方式       | 后果                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| 丢弃（原实现） | 思考期间界面**一片空白**，用户以为卡死                                         |
| 若并入正文     | 用户看到大段"让我想想…不对，应该是…"的**自我修正碎碎念**，且污染上下文与知识库 |

## 二、难点：厂商字段名不统一

| 厂商                                  | 字段                |
| ------------------------------------- | ------------------- |
| DeepSeek / 通义千问(Qwen) / 智谱(GLM) | `reasoning_content` |
| OpenAI o 系列                         | `reasoning`         |

若只支持其中一个，另一半厂商就 silently 失效 —— 这类"不报错但没效果"的问题最难发现。
因此适配器用统一的 `extractReasoning()` 归一化，**调用方无需关心厂商差异**。

## 三、核心设计：正文与思考过程严格分离

这是本方案最重要的契约：

```
ChatResponse.content     ← 正式回答（唯一进入上下文/知识库的内容）
ChatResponse.reasoning   ← 思考过程（仅用于展示，不污染上下文）

ChatChunk.delta          ← 正文增量
ChatChunk.reasoningDelta ← 思考增量
```

**分离的价值**：思考过程是模型的自我推导，含大量试错与自我否定。它应当**可见**（让用户知道在动）
但不应当**入档**（否则几轮对话后上下文被思维链塞满，也会污染知识库）。

## 四、四层实现

| 层                                                        | 改动                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **类型** `core/src/types/index.ts`                        | `ChatResponse.reasoning`、`ChatChunk.reasoningDelta`                                        |
| **适配器** `core/src/adapters/OpenAICompatibleAdapter.ts` | `extractReasoning()` 归一化 `reasoning_content` / `reasoning`；流式与非流式两条路径都接     |
| **引擎** `core/src/agent/AgentEngine.ts`                  | `streamChat` 累积思维链并回调；`run()` 新增可选 `onReasoning`（不传则行为不变）             |
| **服务端** `server/src/index.ts`                          | WS 新增 `reasoning_delta` 消息类型（**不并入 `text_delta`**）；完成日志增加 `reasoningLen`  |
| **前端** `chatStore` / `MessageList` / `ChatInput`        | store 新增 `streamingReasoning`；气泡顶部渲染**可折叠**「思考过程」块；发新消息时清空上一轮 |

### 两个容易忽略的细节

1. **只有思维链、正文还没到时也必须渲染气泡**。
   原逻辑是 `if (streamingText)` 才渲染流式气泡 —— 推理模型思考阶段 `streamingText` 为空，
   界面会**继续保持空白**，等于没修。现改为 `if (streamingText || streamingReasoning)`。
2. **思维链按纯文本渲染**，不进 `dangerouslySetInnerHTML`。
   它是模型自由生成的文本，没必要过 Markdown 渲染器，少一条攻击面。

## 五、测试（8 条，`core/src/__tests__/openai-reasoning.test.ts`）

| 分组   | 用例                                                           |
| ------ | -------------------------------------------------------------- |
| 流式   | DeepSeek 风格 `reasoning_content` → `reasoningDelta`           |
| 流式   | OpenAI 风格 `reasoning` → `reasoningDelta`                     |
| 流式   | **单 chunk 内同时出现也要分开**（互不污染）                    |
| 流式   | 无推理字段时不产生 `reasoningDelta`（普通模型行为不变）        |
| 流式   | 空串 / `null` 不产生 `reasoningDelta`                          |
| 非流式 | `reasoning_content` → `response.reasoning`，且不混入 `content` |
| 非流式 | `reasoning` 字段同样生效                                       |
| 非流式 | 无推理字段时 `reasoning` 为 `undefined`（保持原有响应形状）    |

### 顺带固化的护栏：`pnpm verify:readme-format`

v0.6.30 把 README 改为取原始 Markdown，但这个约束在**服务端配置层**，单测用的是 mock
（mock 会跟着一起改 → 测不出来）。因此新增脚本直接打**真实 GitHub API** 校验格式，
作为独立护栏：

```
✅ README 为原始 Markdown（长度 13541）
✅ 格式校验通过 —— 未回退为 HTML
```

网络不可用或触发限流时**跳过并退出 0**，避免把 CI 卡在外部依赖上。

## 七、已知边界与后续

1. **仅 WS 聊天路径**接通了思考过程。HTTP 流式（`/api/chat` 的 SSE）与自动化任务执行器
   目前仍只用 `onPartialResponse`，思考内容不转发 —— 若这两条路径也需要展示，按同一模式补即可。
2. **思考过程不持久化**：目前只在流式期间可见，本轮结束后清空。若产品希望"回看上次思考过程"，
   需要把它挂到 `ChatMessage` 上（并明确**不参与后续上下文拼装**）。
3. 本次只做了解析与展示；P1-2 的另外两项（provider 预设刷新、缺失 provider 补齐）**尚未动**，
   且刷新模型代际前必须**先联网核实当前型号**，不能凭记忆填。
