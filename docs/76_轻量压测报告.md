## 四、修复实施记录（2026-09-18 晚：①SWR + ②路径修正 + B worker 全部落地）

**压测复跑对比（场景 3）**：

| 指标                           |              修复前 |                                     修复后 |
| ------------------------------ | ------------------: | -----------------------------------------: |
| 慢请求在飞期间 health 最差延迟 | **10015ms**（冻结） |                                 **2ms** ✅ |
| 慢请求本身耗时                 | 10014ms（触发超时） |        10008ms（真实扫描，调用者仍需等待） |
| health 吞吐                    |          2342 req/s | 1792 req/s（含 Worker 启动开销，正常波动） |

**实现要点**（`routes/semantic.ts` 重构）：

1. **② 路径修正**：core `buildSemanticMap` 增加第 4 参 `options.expandToRepoRoot`（默认 true 保持
   原行为）；路由显式 `path` 参数传 false —— 查子目录不再被放大到全仓
2. **B worker**：长驻 `Worker`（eval 模式 + 动态 import core ESM dist），map/search/references
   三个任务的扫描全部在 Worker 内执行，主线程事件循环零阻塞；Worker 内自持 60s 地图缓存
   （search/references 复用不重复扫描）
3. **① SWR**：map 结果缓存过期时**先返回陈旧数据 + 后台重建**（仅冷启动首次需等待 Worker 实际扫描）

**踩坑记录**：

- `require.resolve('@easyagent/core')` 失败（exports 无 main 回退，子路径也全被禁）→
  改为基于模块位置探测 `core/dist/index.js`（兼容 dist/src 两种布局）
- Worker `eval: true` 模式下 **必须显式传 `workerData` 选项**，否则 worker 内 workerData 为 undefined
- Windows 下 `srv.kill()` 后 libuv 断言（worker_threads 竞态）为无害噪音

**遗留**：调用者冷启动首次仍需等待真实扫描（~10s，Worker 内执行）；彻底缩短需增量扫描/
磁盘持久缓存，留待需求驱动。

> ✅ **2026-09-19 已闭环（四轮）**：① 根因是 `extractSymbols` 的 **O(n²) 行号计算**（一个压缩 bundle 占 96% 耗时）
> → 修复后全仓 716 文件冷启从 11s 降到 ~0.5s；② **mtime + size 增量缓存** → 热跑 **~36ms**；
> ③ 补**截断可见化**（超上限不再静默丢弃）；④ 剖析发现瓶颈在**磁盘 I/O（59%）**→ Buffer 直读 + 并发读盘，
> 冷启再降到 **~0.26s**，且**概览端点**从主线程阻塞 618ms → **213ms**。
> 详见 `docs/修复汇总.md` 同日四条。

## 二、关键发现：semantic/map 冻结整个服务

**现象**：带 `refresh=true` 的 `/api/semantic/map` 在飞期间（本机实测 10s+，含 IDE 负载），
**所有并发请求（包括 /api/health）被冻结同样时长** —— Express 单进程事件循环被
`buildSemanticMap`（同步读文件 + 正则扫描）完全占死。

> ⚠️ 本段为 **2026-09-18 压测时点**的记录，保留原样作对照。2026-09-19 优化后该端点
> 冷启 **~0.26s**、热跑（增量缓存命中）**~36ms**，冻结窗口缩短约 40 倍（详见 `docs/修复汇总.md` 同日四条）。

**影响面**：

- 公网部署（82.156.71.231）多用户场景：任何一个用户点"刷新语义地图"，**全体用户的服务冻结 10 秒+**
- 桌面单用户：前端 UI 发起的其他请求同样卡死
- 现有缓解：60s 路由缓存（P1-6 批次加入）只减少重复扫描，**首次/强制刷新仍冻结**

**修复方案（⚠️ 2026-09-18 晚修正推荐 —— 初版推荐方案 A 是错的）**：

| 方案                           |    调用者体验     |                           其他用户被冻结？                           | 解决公网问题？ |
| ------------------------------ | :---------------: | :------------------------------------------------------------------: | :------------: |
| A：202 + setImmediate 后台构建 |     ✅ 不悬挂     | ❌ **仍冻结 10s**（构建仍在主线程同步跑，setImmediate 只是推迟开始） |       ❌       |
| **B：worker_threads（推荐）**  | ⏸ 调用者仍等 ~10s |                            ✅ **不冻结**                             |       ✅       |
| C：前端隐藏入口                |         —         |                ✅ 实际无人触发（API 已有 token 鉴权）                | ✅（实际层面） |

- **方案 A 的误区**：`setImmediate` 只是推迟任务开始，`buildSemanticMap` 一旦执行仍是
  主线程同步 CPU 密集 —— 事件循环照样冻结。它只改善调用者体验。
- **方案 B 最小实现**：新建 worker 文件执行 `buildSemanticMap`（纯函数读文件，worker 内可直接
  import），主线程 `await` worker 结果后再响应 —— 调用者等待 10s 不变，但**其他人不再受影响**。
  注意返回值含 `Map`（symbolIndex/referenceGraph），structuredClone 可传输，但路由层只用
  `topSymbols` 等派生数组，可在 worker 内完成序列化后传回。
- **方案 C**：语义地图仅供 IDE/诊断使用，从前端移除入口；API 有鉴权兜底，实际触发≈0。
- **公网部署前必须做 B 或 C**；A 单独做没有意义（除非与 B 组合改善等待体验）。
