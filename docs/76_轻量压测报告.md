## 二、关键发现：semantic/map 冻结整个服务

**现象**：带 `refresh=true` 的 `/api/semantic/map` 在飞期间（本机实测 10s+，含 IDE 负载），
**所有并发请求（包括 /api/health）被冻结同样时长** —— Express 单进程事件循环被
`buildSemanticMap`（同步读文件 + 正则扫描）完全占死。

**影响面**：
- 公网部署（82.156.71.231）多用户场景：任何一个用户点"刷新语义地图"，**全体用户的服务冻结 10 秒+**
- 桌面单用户：前端 UI 发起的其他请求同样卡死
- 现有缓解：60s 路由缓存（P1-6 批次加入）只减少重复扫描，**首次/强制刷新仍冻结**

**修复方案（建议，未实施）**：
1. **方案 A（推荐，改动小）**：路由改 async —— 缓存未命中/refresh 时立即返回
   `202 { status: 'building' }`，用 `setImmediate` 后台构建完成后写入缓存；
   前端轮询直至就绪。配合前端加"构建中"状态提示。
2. **方案 B（彻底）**：`buildSemanticMap` 迁移到 `worker_threads` —— 不阻塞事件循环，
   但需处理结构化克隆（Map 返回值需序列化），改动面大。
3. **方案 C（产品侧）**：语义地图 API 仅供 IDE/诊断使用，从前端隐藏入口 —— 无代码改动。

**优先级建议**：单用户桌面场景可暂缓；公网部署前应实施方案 A（约 1-2 小时）。

## 三、使用说明

```bash
pnpm bench:load     # 4 场景全跑（双实例：限流关/开），约 30s
```

- 需先构建 server；LLM 端点不在压测范围（瓶颈在上游模型 API）
- 场景 4 的业务处理器报错（无 provider）属预期，只统计状态码
- 数值随机器浮动，看**相对判定**（阻塞倍数、429 是否触发），不要背绝对值
