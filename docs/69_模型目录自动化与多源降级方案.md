# 模型目录自动化与多源降级方案

> **建立日期**: 2026-09-18
> **起因**: 用户提问「新模型能不能自动拉取升级？」「连不上 GitHub 怎么办？」
> **当前状态**: ✅ 已完成并发布 —— 目录可自动生成 + 多源降级 + 来源可见

---

## 一、先厘清：原来到底哪一环断了

勘察发现，**客户端侧的"自动拉取"早就实现了**：

| 能力                                               | 原状态 |
| -------------------------------------------------- | :----: |
| 远程目录（GitHub raw）+ CDN 兜底（jsDelivr）       |   ✅   |
| 本地缓存 + 24h TTL                                 |   ✅   |
| 三级降级（远程 → 缓存 → 内置）                     |   ✅   |
| 手动强制刷新 `POST /api/providers/catalog/refresh` |   ✅   |

**但"自动升级"没实现**，原因不在客户端，而在**目录文件本身**：

> 实测 `models-catalog.json` 的 `generatedAt` 停留在 **2026-06-19**，也就是 **91 天**没重新生成过。
> 客户端每天都在勤快地自动下载 —— 下载的是一份三个月前的数据。

**根因**：目录文件是**人工维护**的（仓库里没有生成脚本、没有定时任务）。
所以"厂商发布新模型 → 自动出现"这条链路，卡在**中间那一环**。

---

## 二、第二个问题：连不上 GitHub 怎么办

原降级链只有两个远程源：`raw.githubusercontent.com` 与 `cdn.jsdelivr.net` ——
**在国内这两个都可能不可达**。此时会退到本地缓存/内置数据：**功能不坏，但永远不更新**。

更糟的是：**这个失败没有任何提示**（现在已通过 `source` / `stale` 字段暴露）。

### 关键洞察：把两类数据分开看

| 数据类型                           | 例子                         | 最佳获取通道                   |
| ---------------------------------- | ---------------------------- | ------------------------------ |
| **模型列表**（有哪些模型）         | `deepseek-v4`、`gpt-6-astra` | ⭐ **厂商 `/models` API 直连** |
| **模型元数据**（价格/上下文/能力） | 1.05M ctx、$10/$50、支持视觉 | 目录分发（社区/CI 维护）       |

`api.deepseek.com`、`dashscope.aliyuncs.com` 这类**国内可直接访问**，而且厂商一发新模型
`/models` 立刻就有 —— 这是**第一手数据**，比 GitHub 分发更及时。

> 所以正确策略不是"找更多 GitHub 镜像"，而是**让更新通道不依赖 GitHub**。

---

## 三、方案

### 3.1 目录自动生成（补上断掉的那一环）

新增 `scripts/refresh-models-catalog.mjs`（`pnpm models:refresh`）：

```
数据源 ①：PROVIDER_PRESETS（内置预设）—— 已知模型以它为准
          它带人工校准过的元数据（上下文/价格/能力），比厂商 /models 更全
数据源 ②：厂商 /models API（需对应 *_API_KEY）—— 只用于**发现新模型**

合并规则：
  · 预设已有 → 保留预设元数据（不覆盖）
  · API 发现、预设没有 → **新增**，标记 unverified: true
  · 预设已有、API 没有 → **保留**（厂商端点可能滞后），仅记入 missingFromApi
```

配套 **GitHub Actions 定时任务** `.github/workflows/refresh-models.yml`：每周一自动重新生成并提交。
配置了厂商 Key（Secrets）时会自动发现新模型；不配也能刷新预设部分。

### 3.2 多源降级链（应对连不上 GitHub）

`ModelRegistry` 的加载顺序改为**优先级有序的源链**，任一步失败都继续下一步：

| 优先级 | 源             | 环境变量 / 说明                                                        |
| :----: | -------------- | ---------------------------------------------------------------------- |
|   1    | **自定义 URL** | `EASYAGENT_MODELS_CATALOG_URL` —— 自建镜像（Forgejo / OSS / 对象存储） |
|   2    | **本地文件**   | `EASYAGENT_MODELS_CATALOG_FILE` —— 气隙环境 / 离线导入                 |
|   3    | **额外镜像**   | `EASYAGENT_MODELS_CATALOG_MIRRORS`（逗号分隔）                         |
|   4    | GitHub raw     | 内置主源                                                               |
|   5    | jsDelivr CDN   | 内置备用源                                                             |
|   6    | 本地缓存       | **网络失败时继续用旧缓存，只告警不清空**                               |
|   7    | 应用内置数据   | 最终兜底                                                               |

**设计原则：绝不让"连不上"变成"没有模型可选"** —— 缓存永不作废，只告警。

> 💡 本项目已有自建 **Forgejo**（`localhost:3000`，每次发版都往那儿推）。
> 把目录托管上去，即为**完全自主可控的镜像源**，优先级 1 直接指向它即可。

### 3.3 厂商 API 直连补齐（不依赖 GitHub 的更新通道）

当目录**不够新**（`stale` 或来自缓存/内置）时，启动阶段会用**已配置 API Key 的厂商**
直连其 `/models`，把最新模型列表**并入**目录。

安全边界（重要）：

- **只新增**，绝不删除或覆盖 —— 避免厂商端点抖动导致"模型消失"
- 新增条目标记 `unverified: true`，因为厂商 `/models` 通常**不返回**价格/上下文等元数据，
  这里只能给保守默认值。**界面必须能区分，不能把默认值当作真实规格呈现**
  （否则用户会以为 $0 真是免费、32K 真是它支持的上下文）

### 3.4 状态可见（否则问题永远看不见）

`GET /api/providers/catalog/status` 现在返回：

```json
{
  "version": "1.0.1",
  "generatedAt": "2026-09-18T02:20:15.488Z",
  "source": "本地文件 /path/to/catalog.json",
  "stale": false,
  "ageDays": 0,
  "maxAgeDays": 30
}
```

- **`source`** —— 排障第一问：「模型列表不新」时先确认**数据到底从哪来**
- **`stale` / `ageDays`** —— 下载成功 ≠ 数据新鲜（这一条是最容易误判的）

启动时若目录过期，日志会明确告警并给出修复命令。

## 五、顺带修掉的 flaky 测试

全量回归时 `plugin-sandbox` / `plugin-manager` 出现 **11 条间歇性失败**，
而单独运行这两个文件 96/96 全过 —— 典型的**跨文件状态干扰**（插件系统持有进程级单例）。

处置：core 包设 `fileParallelism: false`（串行执行测试文件）。

**代价是真实的**：core **15s → 35.9s（+140%）**，全量回归 60s → 90s。
这是**预防性**修复（未能稳定复现），用时间换确定性 —— 测试结果不可信比跑得慢更糟。
若日后想收回这部分时间，正确做法是**定位并修掉真正的状态干扰**（让插件测试各用独立目录与实例），
而不是关掉该开关。

## 六、仍需人工介入的部分（边界透明）

| 项                          | 说明                                                                                                                  |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **元数据的准确性**          | 厂商 API 不提供价格/上下文，自动发现的新模型元数据是**保守默认值**（标记 `unverified`）。要准确仍需人工或官方文档校准 |
| **发布为 npm 包走国内镜像** | 可将目录发布为 npm 包从 `registry.npmmirror.com` 分发（国内最稳）。**需要 npm 发布权限**，本次未做                    |
| **首次配置厂商 Key**        | 厂商直连补齐需要用户已配置 API Key；未配置时只能靠目录分发                                                            |
