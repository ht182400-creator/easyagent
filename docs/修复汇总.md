## 2026-09-19 — 语义扫描第四轮：剖析驱动（Buffer 直读 + 并发读盘 + 概览不再阻塞主线程）

### 先剖析，再动手（本轮最大教训）

分阶段剖析本仓库 717 文件 / 35MB：
| 阶段 | 耗时 | 占比 |
|------|------|------|
| **纯读盘** | **243ms** | **59%** |
| 正则解析 | 150ms | 36% |
| 目录遍历 | 20~41ms | 5% |

→ 瓶颈是**磁盘 I/O，不是 CPU**。所以本轮没做"加线程跑解析"（原计划），而是治 I/O 与无谓开销。

### 变更

| #   | 内容                                                                                                                                                                                                                                                                                       | 效果依据                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| 1   | **`analyzeFromBuffer()`**：统一由 Buffer 生成结果 —— 行数**按字节统计**（等价 `split('\n').length` 但不解码、不建数组）；`size` 直接取 `buf.length`（旧实现 `Buffer.byteLength(content)` 把整个字符串重编一遍）；**无符号模式语言（md/json/html/css）直接返回**，跳过 utf-8 解码与符号扫描 | 省掉 35MB 的解码/再编码与整表分配 |
| 2   | **`buildSemanticMapAsync()`**：stat 判增量缓存 → 未命中者**限流并发读盘**（默认 16）→ 读一个解析一个（I/O 与 CPU 交织）；同步版保留给工具层/单测，两者共用 `assembleMap()`                                                                                                                 | I/O 无法在同步代码里重叠          |
| 3   | **`getCodebaseOverviewAsync()`** + 概览行数缓存：旧实现逐个 `readFileSync(utf-8)+split`，**在主线程同步阻塞 ~240ms**；改为并发读 + 按字节数行                                                                                                                                              | 该端点此前会冻结事件循环          |
| 4   | Worker / 概览路由改走异步版（Worker 内带旧 dist 回退逻辑）                                                                                                                                                                                                                                 | 渐进增强，无破坏性                |
| 5   | 忽略判定**预编译**（旧实现每文件都为 `*.min.js` 等通配模式 `new RegExp`，717 文件上千次编译）                                                                                                                                                                                              | 目录遍历阶段                      |

### 实测（本机，各 3 次取中位数 —— 单次抖动可达 ±30%）

| 场景                      | 修复前    | 修复后              | 提速      |
| ------------------------- | --------- | ------------------- | --------- |
| 地图 同步冷启             | 367ms     | **257ms**（并发版） | 1.42×     |
| 地图 热跑（增量缓存命中） | —         | **~36ms**           | —         |
| **概览（原主线程阻塞）**  | **618ms** | **213ms**           | **2.90×** |

- 一致性：并发版与同步版 `stats` / 符号索引 / 文件顺序 / 概览文件树**完全一致**（有测试守护）
- 累计：会话起点 11,046ms → 现在 **257ms（43×）**

### 一并验证的"伪优化"（记录以免重走）

- `UV_THREADPOOL_SIZE=16`：三组对照 253ms / 232ms / 248ms → **属噪声，未采纳**
- 单独提高 `concurrency`（4/16/32/64）：330/368/333/284ms → 也是噪声，**保持默认 16**

### 验证

- core ✅ **1108/1108**（+4：行数等价性、并发三件套）· 全量 ✅ **1809/1809** · `verify:all` ✅ 10/10 · 0 诊断

### 后续可选（剩余空间，已登记 `docs/44` #19）

剖析显示冷启剩余成本集中在**正则解析 ~150ms（CPU，约占 36%）**，三个候选（按性价比待评估）：

| 候选 | 做法                                                                                                                   | 代价                             |
| ---- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| A    | **worker_threads 分片解析**：每个线程读各自 shard 并解析（线程内用 sync 读 → 绕过 libuv 默认 4 线程池），兼收 I/O 并行 | 结构化克隆回传开销；实现复杂度中 |
| B    | **tree-sitter 替换正则**：顺带解决"注释/字符串里的伪符号"准确率问题                                                    | 引入原生依赖（跨平台构建）       |
| C    | **廉价预筛**：模式执行前先 `indexOf` 锚点串（如 `'function '`）                                                        | 收益最小，但改动最小、零风险     |

## 2026-09-19 — 语义扫描 11s → 0.14s：O(n²) 行号计算 + 压缩产物 + 上限截断

### 现象

用户质疑「全仓 300 文件扫描为何要 11s」。剖析后发现耗时**极度不均**：

```
10345.9ms  lines=26    syms=25804  .obsidian\plugins\obsidian-excalidraw-plugin\main.js
   244.0ms  lines=20876 syms=8483   .obsidian\plugins\dataview\main.js
其余 298 个文件合计 ≈ 380ms
```

即**一个压缩成单行的第三方插件 bundle 吃掉 96% 耗时**。

### 根因（四处叠加）

1. **O(n²) 行号计算（主因）**：`extractSymbols` 对**每个符号匹配**都 `content.substring(0, matchPos)`
   - 对前缀全文匹配 `\n` 数行号 → 复杂度 O(符号数 × 文件长度)。该 bundle 有 25804 处匹配 → 10.3s
2. **签名提取同样复制尾串**：`content.substring(matchPos + match[0].length)` + `indexOf(')')`
   → 每匹配 O(文件长度)
3. **压缩产物拦不住**：只按文件名忽略 `*.min.js` / `*.bundle.js`，而它叫 `main.js`；
   且 `.obsidian/`（编辑器数据目录，内含 vendored 插件）未被忽略
4. **上限截断**：本仓库实有 717 个可扫描文件（516 个代码文件）。`maxFiles=300` 时（代码优先排序后）
   300 个名额全被代码文件占满，仍有 **216 个代码文件（42%）** 与全部 114 个 `.md` / 73 个 `.json`
   未被纳入 —— 语义地图一直是残缺的；且**静默截断**，界面无任何提示

### 修复（`packages/core/src/semantic/SemanticAnalyzer.ts` 等）

| 优化                                                     | 说明                           |
| -------------------------------------------------------- | ------------------------------ |
| `buildLineIndex()` 建索引 + `lineAt()` 二分查找          | 行号/列号 O(1)，彻底去掉 O(n²) |
| 签名提取改 `indexOf(')', from)` + 500 字符窗口           | 不再复制尾串（去 O(n·m)）      |
| `looksMinified()`（行数 ≤50 且平均行长 >2000）→ 跳过     | 拦掉病态产物文件               |
| `MAX_SYMBOLS_PER_FILE = 3000`（标签 break）              | 兜底无界消耗                   |
| `IGNORE_PATTERNS` 增 `.obsidian` / `vendor`              | 不扫编辑器数据目录             |
| 默认 `maxFiles` 300 → **1000**（路由 / Tool / 概览同步） | 全仓覆盖                       |

### 实测（本仓库）

| 场景                       | 修复前   | 修复后                                            |
| -------------------------- | -------- | ------------------------------------------------- |
| 300 文件扫描               | 11,046ms | **144ms（63×）**                                  |
| 最慢单文件                 | 10,346ms | **5.1ms**                                         |
| 全仓 717 文件（上限 1000） | —        | **917ms**，符号 38,251（typescript 292 / tsx 86） |
| server 包测试耗时          | 39.5s    | **8.2s**                                          |

### 业界做法调研（本次查阅）

| 方案               | 代表                                                          | 思路                                                    | 与本项目的关系                                                           |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------ |
| 不建索引，极致单遍 | **ripgrep**                                                   | SIMD + 非回溯正则 + **并行目录遍历** + ignore 规则      | 我们的瓶颈其实在"正则外的 O(n²) 循环"，**不在正则引擎** → 已按此思路修复 |
| trigram 倒排索引   | **zoekt / microsoft tgrep / csearch(Russ Cox)**               | 建 trigram 索引 + 内存映射（索引≈语料 10%），毫秒级检索 | 适合"纯搜索"；建索引本身有成本，暂不需要                                 |
| 增量语法解析       | **tree-sitter**（codebase-memory-mcp / realtime-indexing 等） | 只重解析变更区间，准确率远高于正则                      | 准确性天花板最高，代价是引入原生依赖                                     |
| 按需 + 增量缓存    | **LSP / IDE**                                                 | 只解析被查询文件；按 mtime/size 跳过未变更文件          | **下一步最划算的方向**（见下）                                           |

### 后续可选（未做，按性价比排序）

1. **mtime + size 指纹增量缓存**：已扫过的文件只重解析变更的（二次调用几乎零成本）
2. **worker_threads 并行遍历/解析**：单线程 → 多核（当前 0.9s 里多数是 CPU 正则）
3. **tree-sitter 替换正则**：符号准确率提升（能区分注释/字符串里的伪符号）

### 验证

- core ✅ **1097/1097**（+2 条性能守护用例：大量符号线性耗时 / 压缩产物被跳过）
- 全量回归 ✅ **1798/1798**（6 包）· `verify:all` ✅ **10/10** · `prettier --check` ✅ 0 不符

## 2026-09-19 — 自动化三修：立即触发无反馈 / 状态文案误导 / 人在环路（HITL）

### A. 「点击立即触发不管用」

- **根因**：「立即触发」功能卡片的行为只是 `scrollIntoView` 到任务列表 —— 列表本来就在视野内时，
  点击后毫无反馈，看起来像按钮坏了
- **修复**：卡片行为改为语义明确 —— **定时执行 → 直接打开创建弹窗**、**立即触发 → 打开任务选择器**
  （列出所有任务，点任一立刻执行；暂停中的任务也支持手动跑一次）、执行历史 → 展开面板

### B-0. 任务卡操作按钮语义不清（同日追加）

- **问题**：旧版「立即执行」与「启用/暂停」**都是三角形图标**（▶），同一个卡片里出现两个 ▶，
  用户无法判断哪个是"跑一次"、哪个是"开关调度"（实报：容易理解错误）
- **修复**：改为**图标 + 文字**并换成语义匹配的图标 ——

## 2026-09-18 — 实现 AnthropicAdapter（P1-2 provider 覆盖收尾）

### 现象

P1-2 指出「缺 Anthropic / Google」。上一版补齐了 Google，并发现适配器路由对

### 根因

Anthropic **Messages API 与 OpenAI 格式在五个层面都不同**，无法复用现有适配器：

| ------------ | ----------------------- | ---------------------------------------- |

| `max_tokens` | 可选                    | **必填**（缺失直接 400）                 |
| 流式         | `data:` 单事件流        | **命名事件**（`content_block_delta` 等） |
| 工具         | `tool_calls` 数组       | **`tool_use` / `tool_result` 内容块**    |

- 新增 `packages/core/src/adapters/AnthropicAdapter.ts`（约 430 行）

- `fetchModelsFromProvider` 增加 Anthropic 分支（`x-api-key` + `anthropic-version`，解析 `display_name`）
  —— 让 Anthropic 也能**直连刷新模型清单**，不必只靠硬编码

### 实现中处理的三个易错点

1. **`max_tokens` 必填** —— 取 `options.maxTokens` → 模型 `maxOutputTokens` → 兜底 4096
2. **工具参数分片** —— Anthropic 用 `input_json_delta.partial_json` **分片**下发，

3. **图片块** —— Anthropic 的图片 `source` **只接受 base64**，URL 形式直接 400；
   base64 原样透传，URL 降级为文字说明（宁可少一张图，也不要整条请求失败）

`thinking` 块接入 v0.6.31 的 `reasoningDelta` 契约，与推理模型行为一致。

### 新增测试 16 条（`anthropic-adapter.test.ts`）

## 2026-09-18 — 校验体系消除「空白 = 通过」盲区

### 现象

校验脚本的常见用法是过滤输出：

```powershell
node scripts/verify-server-routes.mjs 2>&1 | Select-String '✅ 路由|❌'
```

过滤只保留含特定标记的行 —— 一旦脚本崩溃、走"跳过"分支或输出格式变化，
结果就是**一片空白**，而空白极易被误读为"没有 ❌ = 通过"，**实际上一次都没校验**。

### 根因

1. 判据依赖**人眼过滤字符串**，而非退出码
2. `verify-readme-format.mjs` 网络异常时**静默退出 0**（只打印一行 ⚠️），
   与"通过"在过滤视角下无法区分

### 修复

- 新增 **`scripts/verify-all.mjs`（`pnpm verify:all`）**：
  退出码 + 机器可读标记判定；PASS/FAIL/**SKIP** 三类都显式列出；
  失败项自动打印输出尾部；支持 `--list` / `--only` / `--skip`；90s 超时保护
- 全部 5 个 `verify-*.mjs` 结尾统一输出 `__VERIFY_STATUS__=PASS|FAIL|SKIP`
- README 校验的跳过分歧改为**显式 `⚠️ SKIP` + 标记**

### 状态契约（新增约定）

| 状态 | 含义                          | 退出码 |
| ---- | ----------------------------- | :----: |
| PASS | 校验通过                      |   0    |
| FAIL | 发现真实问题                  |   1    |
| SKIP | **未做校验**（网络/环境原因） |   0    |

⚠️ `SKIP` 退出码为 0 但**不可当作通过** —— `verify-all` 会单独列出并提示。

### 验证

- `pnpm verify:all` ✅ 5/5 通过，退出码 0
- **负向测试 1**：首跑因脚本路径缺 `scripts/` 前缀报 `MODULE_NOT_FOUND`
  → 汇总为 ❌ 5 失败，**未静默通过**（正是该设计要的效果）
- **负向测试 2**：README 校验对不存在仓库返回 404 → 输出 `__VERIFY_STATUS__=SKIP`

- 统一入口：`scripts/verify-all.mjs`

## 2026-09-18 — 消除远程 HTML 信任面：服务端 README 改取原始 Markdown

### 现象

v0.6.29 把「GitHub 远程 README 裸 HTML 无消毒」修成了「取回后 DOMPurify 消毒」。

| ------ | ---------------------------------- | ------------------------------------------ |

| 方法   | `getReadmeHtml()`                  | `getReadmeMarkdown()`                      |

1. **信任面被消除而非过滤** —— 不存在"远程 HTML 进 DOM"这一步

## 2026-09-18 — P1-4 前端 Markdown 渲染加固：修掉两个 XSS 缺口 + 补上表格/代码高亮

### 现象

审核报告 D9 记录了「Markdown 渲染器可构造属性逃逸」。实际勘察发现问题面更宽：
**3 处渲染点**、**2 类安全缺口**、**1 处样式静默失效**。

| #   | 缺口                   | 攻击样例                                                                 |
| --- | ---------------------- | ------------------------------------------------------------------------ |
| ①   | `"` 未转义 → 属性逃逸  | `[链接](x" onmouseover="alert(1))` 拼出 `<a href="x" onmouseover="...">` |
| ②   | **URI 协议完全不过滤** | `[点我](javascript:alert(1))` **点击即执行**                             |

| 路径                               | 手段                                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| 本地 Markdown → `renderMarkdown()` | `html:false` 转义原始 HTML + `validateLink` 协议白名单 + 链接统一 `rel="noopener noreferrer"` |
| 远程不可信 HTML → `sanitizeHtml()` | DOMPurify 消毒（README 唯一入口）                                                             |

代码高亮按需注册 16 种语言，并补了 `js/ts/sh/py/yml/html` 等 20 组别名（AI 生成的围栏标签很随意）。

### 新增测试

## 2026-07-02 21:55 — 方案 D 三连 Bug 修复：manifest 缺失 / 路径硬编码 / base 404

### 现象

用户截图：插件市场页面右上角反复弹出"安装失败：插件缺少 manifest.json 文件"提示横幅。手动 `GET C:\Users\ht182\.easyagent\plugins\obsidian-doc-viewer\` 确认目录为空。

### 根因（三层叠加）

#### Bug 1: `extractZip` 把平铺 plugin.zip 误判为 GitHub zipball

**位置**：`PluginMarketService.ts:551-553`  
**问题**：原代码用 `dirs.find(d => d.isDirectory() && ...)` 找第一个子目录，作为 GitHub zipball 的包装层。但我们 CI 打的 `plugin.zip` 是**平铺结构**（`manifest.json` + `plugin.js` + `dist/` 三个顶层项），`dist/` 是第一个也是唯一子目录，被误判为包装层。  
**结果**：只把 `dist/` 内容拷到 pluginDir，`manifest.json`/`plugin.js` 被遗弃在 tmpDir，然后 line 464 `existsSync(manifestPath)` 失败 → 抛"缺少 manifest.json" → line 494 catch 清理 pluginDir → 用户看到的目录是空的。

#### Bug 2: `docViewerDistPath` 硬编码 `obsidian-doc-viewer`

**位置**：`server/src/index.ts:3211`  
**问题**：插件目录名实际是 GitHub 仓库名 `easyagent-plugin-obsidian-doc-viewer`（`pluginIdToName` 取 `id.split('/')[1]`），但 Server 端硬编码 `obsidian-plugin-obsidian-doc-viewer`（即 `easyagent-plugin-obsidian-doc-viewer` 的简写），两个不一致导致 Server 永远找不到 dist。

#### Bug 3: vite `base: '/'` 导致资源 404

**位置**：插件仓库 `vite.config.ts:7`  
**问题**：HTML 里引用 `/assets/index-*.js` 绝对路径，浏览器在 `http://localhost:3456/doc-viewer/` 下解析为 `http://localhost:3456/assets/...`，但 Server 的 `app.use('/doc-viewer', ...)` 只在 `/doc-viewer` 前缀下托管 → 404。

### 关键教训

1. **`extractZip` 必须区分 zipball 模式 vs 平铺模式**：不要仅凭"第一个子目录"判断，应该用标记文件（manifest.json/package.json）区分。
