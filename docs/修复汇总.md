## 2026-09-18 — 元数据诚实性（unverified 展示）+ 堵住复发三次的组件类名静默失效

### 现象
v0.6.33 引入 `unverified`（厂商 API 直连发现的新模型，元数据是保守默认值）后，**界面从未呈现**。
补 UI 时核实类名，又发现 **6 处徽章类名在 CSS 中根本不存在**。

### 根因
**① `unverified` 在服务端边界被丢弃** —— 服务端响应是**逐字段重新映射**的（非整对象透传）：

| 环节 | 状态 |
|------|:---:|
| `ModelRegistry.mergeModels()` | ✅ 设置 |
| `ConfigManager.mergeRemoteModels()` | ✅ 整对象 spread，保住 |
| `formatPresetModel()` / `/api/providers` | ❌ **逐字段挑选，丢掉** |
| 前端类型 | ❌ 压根没有该字段 |

后果是**主动误导**：`¥0/¥0` 被读成"免费"、`32K ctx` 被当成真实上下文 —— 而实际是"我们不知道"。

**② 组件类名静默失效（第三次复发）**：

| 时间 | 现象 |
|------|------|
| P0-5 | `tailwind.config.js` 引用未定义的 CSS 变量 |
| v0.6.29 | `prose prose-invert` 依赖未安装的插件 |
| **v0.6.36** | `badge-green`(4) / `badge-yellow`(1) / `badge-blue`(1) 均不存在（实有 `badge-success/warning/error/info/neutral`） |

**共同点：写错类名不报错，只是"看起来有点不对"。三次都是偶然发现，不是被检出的。**

### 修复
**① `unverified` 全链路打通**
- 服务端：`formatPresetModel` / `/api/providers` / `/api/providers/all-models` 三处补透传；
  core 的 `ModelInfo` 显式声明 `unverified?: boolean`
- 前端 `Providers.tsx` + `ChatInput.tsx`：
  - 徽章 `⚠️ 未校准`（`badge-warning`），悬停给出完整解释
  - 上下文显示 `~32K ctx`（`~` 标出是默认值）
  - **价格不显示 `¥0/¥0`，改为"价格未知"** —— 那条会被读成"免费"，属主动误导
  - 能力图标旁附 `⚠️`

**② 新增组件类名门禁** `scripts/verify-component-classes.mjs`（`pnpm verify:classes`）
- 解析 CSS 已定义类名 → 扫描源码 `className` 字面量 → 报出"被使用但未定义"
- **用显式家族列表而非自动派生前缀**：自动派生会把 Tailwind 自身命名空间
  （`overflow-hidden` 等）也纳入校验 → 大量误报
- 已登记进 `verify:all`（现 8 项）

### 门禁做了双向验证
只验证"能通过"是不够的，必须证明它**真的能失败**：

| 验证 | 结果 |
|------|------|
| 正常运行 | ✅ 46 个已定义类 / 91 个源码文件 / 18 个组件类 → 零未定义 |
| **负向测试**（注入含 `badge-green`、`btn-outline-primary` 的临时文件） | ✅ **精准抓到 2 个** + 文件位置，退出码 1 |

### 新增测试 3 条
`/api/providers` 透传 / 类型必须为布尔或未定义 / `/api/providers/all-models` 同样透传
（该链路是逐字段映射，极易被静默丢弃）。

### 验证
- 服务端测试 ✅ 33/33（+3）· **全量回归 ✅ 1729/1729，0 失败**
- **`verify:all` ✅ 8/8** · 类型检查 ✅ 0 诊断 · 构建 core/server/web ✅ 全通过

### 沉淀的约定
1. **服务端响应是逐字段映射的** → 新增字段必须同时改三处，否则静默丢失
2. **不知道就显示"不知道"** → 默认值须用 `~` / `未知` 区分，不得伪装成实测值
3. **引用样式类名前先确认存在** → 新家族登记进 `COMPONENT_FAMILIES`；校验用 `pnpm verify:classes`

## 2026-09-18 — 实现 AnthropicAdapter（P1-2 provider 覆盖收尾）

### 现象
P1-2 指出「缺 Anthropic / Google」。上一版补齐了 Google，并发现适配器路由对
`apiFormat='anthropic'` 会**静默回退**到 OpenAI 适配器（已改为显式抛错）。本版把该分支真正实现。

### 根因
Anthropic **Messages API 与 OpenAI 格式在五个层面都不同**，无法复用现有适配器：

| 层面 | OpenAI | Anthropic |
|------|--------|-----------|
| 鉴权 | `Authorization: Bearer` | `x-api-key` + **`anthropic-version`** 头 |
| 系统提示 | messages 里 role=system | **顶层 `system` 字段** |
| `max_tokens` | 可选 | **必填**（缺失直接 400） |
| 流式 | `data:` 单事件流 | **命名事件**（`content_block_delta` 等） |
| 工具 | `tool_calls` 数组 | **`tool_use` / `tool_result` 内容块** |

### 修复
- 新增 `packages/core/src/adapters/AnthropicAdapter.ts`（约 430 行）
- `AdapterFactory` 的 `case 'anthropic'` 由「显式抛错」改为返回该适配器
- `ProviderId` 新增 `'anthropic'`；新增预设（4 个模型，`apiFormat: 'anthropic'`）
- `fetchModelsFromProvider` 增加 Anthropic 分支（`x-api-key` + `anthropic-version`，解析 `display_name`）
  —— 让 Anthropic 也能**直连刷新模型清单**，不必只靠硬编码

### 实现中处理的三个易错点
1. **`max_tokens` 必填** —— 取 `options.maxTokens` → 模型 `maxOutputTokens` → 兜底 4096
2. **工具参数分片** —— Anthropic 用 `input_json_delta.partial_json` **分片**下发，
   必须按 `index` 累积到 `content_block_stop` 才能拼成完整 JSON（已加专测锁定）
3. **图片块** —— Anthropic 的图片 `source` **只接受 base64**，URL 形式直接 400；
   base64 原样透传，URL 降级为文字说明（宁可少一张图，也不要整条请求失败）

`thinking` 块接入 v0.6.31 的 `reasoningDelta` 契约，与推理模型行为一致。

### 新增测试 16 条（`anthropic-adapter.test.ts`）
请求头（x-api-key 且**不得**出现 Bearer）、`system` 抽到顶层、`max_tokens` 必填、
工具转 `input_schema`、`tool_choice` 结构、工具结果转 `tool_result` 块、
`stop_reason` 四项映射、thinking→reasoning、流式文本/思考/工具分片累积、
`validateConnection` 最小请求与异常不抛出。

### 验证
- Anthropic 适配器 + 预设测试 ✅ 30/30 · 目录 ✅ 13 家 / 58 模型
- **全量回归 ✅ 1726/1726，0 失败** · **`verify:all` ✅ 7/7**

### 边界（如实说明）
预设中 4 个模型 ID 的**命名规范与家族版本**来自 2026-08 公开汇总清单，
与本项目 2026-09 检索一致；但 Anthropic **未提供机器可校验的公开清单**，
无法像 OpenAI 那样逐条比对官方页。已打通 `GET /v1/models` 直连作为补偿。

### 关联
- `docs/70_Provider覆盖与Anthropic适配器方案.md` §4.4

## 2026-09-18 — 补齐 Google provider + 修复适配器路由的静默失败陷阱

### 现象
审核报告 P1-2 指出「缺 Anthropic / Google 两个 provider」。补齐过程中发现一个**更隐蔽**的问题。

### 修复
**① 补齐 Google Gemini**（走官方 OpenAI 兼容端点，无需新适配器）
- baseURL `https://generativelanguage.googleapis.com/v1beta/openai/`（**末尾 `/openai/` 不能漏**，漏了会 404）
- 鉴权为标准 Bearer，env `GEMINI_API_KEY`，`apiFormat: 'openai'`
- **预设只放一个已核实的模型**（`gemini-3.5-flash`），而不是硬编码一份"看起来完整"的清单 ——
  Google 官方文档明确说明示例模型名仅供参考，权威清单应以 `models.list` 实时返回为准。
  真实清单由 v0.6.33 建立的**厂商直连通道**动态补齐。

**② 🛡️ 修复适配器路由的静默失败陷阱**
`AdapterFactory.create()` 的 switch 原本只有 `custom` 与 `default: openai` 两个分支，
而类型里 `apiFormat` 是 `'openai' | 'anthropic' | 'custom'` —— **`'anthropic'` 没有任何分支处理**。
一旦有人配 `apiFormat: 'anthropic'`，会**静默落到 default**，用 OpenAI 格式的适配器去请求
Anthropic 的 API：得到 400/401，而错误信息与真实原因（格式选错）**毫无关系**，排查成本极高。

处置：新增 `case 'anthropic'` **显式抛错**（附明确指引）。
> **设计原则：明确的失败远好于悄悄用错的实现。**

### 新增测试 14 条（`provider-presets.test.ts`）
- 预设完整性：12 家的必需字段齐全、每家至少 1 个模型且 `defaultModel` 在列表内、id 不重复、baseURL 为 https
- Google 专项：baseURL 精确匹配（锁住 `/openai/`）、格式、env 名、工厂可创建适配器
- 🛡️ `apiFormat=anthropic` **必须抛错**，不得静默回退

### 验证
- 预设与路由测试 ✅ 14/14 · 目录刷新 ✅ 12 家 / 54 模型（无重复 ID、合计一致）
- **全量回归 ✅ 1710/1710，0 失败** · **`verify:all` ✅ 7/7**

### 未完成（透明）
**Anthropic 适配器尚未实现** —— Messages API 与 OpenAI 在鉴权头、`system` 位置、
`max_tokens` 必填、流式事件类型、工具调用块结构五个层面均不同，必须专用适配器。
方案与实现要点见 `docs/70` §四，预估约 1 人日。

### 关联
- `docs/70_Provider覆盖与Anthropic适配器方案.md`

## 2026-09-18 — 模型目录自动化与多源降级（回答「新模型能否自动升级」「连不上 GitHub 怎么办」）

### 现象
用户提问：厂商发新模型时 EasyAgent 能否自动升级？连不上 GitHub 怎么办？

### 根因（实测，与直觉相反）
**客户端侧的"自动拉取"早就实现了**（远程目录 + CDN 兜底 + 24h 缓存 + 三级降级 + 手动刷新）。
断掉的是**中间那一环**：

> `models-catalog.json` 的 `generatedAt` 停留在 **2026-06-19** —— **91 天**没重新生成过。
> 客户端每天勤快地自动下载，下载的是一份**三个月前**的数据：**"自动拉取"有了，"自动升级"并没有**。

原因：目录文件**人工维护**（仓库里无生成脚本、无定时任务）。
另外原降级链只有 `raw.githubusercontent.com` + jsdelivr —— **国内两者都常不可达**，
且失败**没有任何提示**。

### 修复（三部分）

**① 目录自动生成**：新增 `scripts/refresh-models-catalog.mjs`（`pnpm models:refresh`）
- 内置预设为基准（元数据已校准）+ 厂商 `/models` 只用于**发现新模型**
- 合并规则：只增不删、不覆盖已校准元数据、新增标记 `unverified`
- 配套 GitHub Actions **每周定时**重新生成并提交

**② 多源降级链**（任一步失败继续下一步）：
`自定义 URL → 本地文件 → 额外镜像 → GitHub raw → jsDelivr → 本地缓存 → 应用内置`
- 新增环境变量：`EASYAGENT_MODELS_CATALOG_URL` / `_FILE` / `_MIRRORS`
- **原则：绝不让"连不上"变成"没有模型可选"** —— 缓存永不作废，只告警

**③ 厂商 API 直连补齐**（不依赖 GitHub 的更新通道）：
目录 `stale` 或来自缓存/内置时，用已配置 Key 的厂商直连 `/models` 并入最新模型列表。
**只增不删**，新增标记 `unverified`（厂商端点不返回价格/上下文，不能假装元数据是准的）。

**④ 状态可见**：`/api/providers/catalog/status` 返回 `source` / `stale` / `ageDays` / `maxAgeDays`，
启动时目录过期会明确告警 —— 让"看不见的过期"变成看得见的事实。

### 顺带修掉的 flaky 测试
全量回归时 `plugin-sandbox` / `plugin-manager` 出现 **11 条间歇性失败**，
单独跑这两个文件 96/96 全过 → 典型**跨文件状态干扰**（插件系统持有进程级单例）。
处置：core 设 `fileParallelism: false`。**代价真实**：core 15s → 35.9s（+140%），
但测试结果不可信比跑得慢更糟。属**预防性**修复（未能稳定复现）。

### 验证
- 目录生成 ✅ 11 家 / 52 模型（原 40）· 过期检测 ✅（修复前报 91 天 FAIL，重建后 PASS）
- 多源降级端到端 ✅ 5/5（`pnpm verify:catalog-sources`，含缓存备份还原）
- 新增单元测试 16 条 · **全量回归 ✅ 1696/1696，0 失败** · **`verify:all` ✅ 7/7**

### 边界（透明）
1. 自动发现的新模型**元数据是保守默认值**（标记 `unverified`），准确值仍需人工/官方文档校准
2. 发布为 npm 包走 npmmirror（国内最稳分发）**需 npm 发布权限**，本次未做
3. 厂商直连补齐需用户已配置对应 API Key

## 2026-09-18 — 校验体系消除「空白 = 通过」盲区

### 现象
校验脚本的常见用法是过滤输出：
```powershell
node scripts/verify-server-routes.mjs 2>&1 | Select-String '✅ 路由|❌'
```
过滤只保留含特定标记的行 —— 一旦脚本崩溃、走"跳过"分支或输出格式变化，
结果就是**一片空白**，而空白极易被误读为"没有 ❌ = 通过"，**实际上一次都没校验**。

### 根因
1. 判据依赖**人眼过滤字符串**，而非退出码
2. `verify-readme-format.mjs` 网络异常时**静默退出 0**（只打印一行 ⚠️），
   与"通过"在过滤视角下无法区分

### 修复
- 新增 **`scripts/verify-all.mjs`（`pnpm verify:all`）**：
  退出码 + 机器可读标记判定；PASS/FAIL/**SKIP** 三类都显式列出；
  失败项自动打印输出尾部；支持 `--list` / `--only` / `--skip`；90s 超时保护
- 全部 5 个 `verify-*.mjs` 结尾统一输出 `__VERIFY_STATUS__=PASS|FAIL|SKIP`
- README 校验的跳过分歧改为**显式 `⚠️ SKIP` + 标记**

### 状态契约（新增约定）
| 状态 | 含义 | 退出码 |
|------|------|:---:|
| PASS | 校验通过 | 0 |
| FAIL | 发现真实问题 | 1 |
| SKIP | **未做校验**（网络/环境原因） | 0 |

⚠️ `SKIP` 退出码为 0 但**不可当作通过** —— `verify-all` 会单独列出并提示。

### 验证
- `pnpm verify:all` ✅ 5/5 通过，退出码 0
- **负向测试 1**：首跑因脚本路径缺 `scripts/` 前缀报 `MODULE_NOT_FOUND`
  → 汇总为 ❌ 5 失败，**未静默通过**（正是该设计要的效果）
- **负向测试 2**：README 校验对不存在仓库返回 404 → 输出 `__VERIFY_STATUS__=SKIP`

### 关联
- 统一入口：`scripts/verify-all.mjs`

## 2026-09-18 — 推理模型「思考过程」支持：思维链与正文分离（P1-2 之一）

### 现象
审核报告 P1-2 指出「推理通道 `reasoning_content` 未解析」。推理模型（DeepSeek-R1 /
Qwen3-thinking / GLM-Z1 / o 系列）会先输出思维链再给正式回答，原实现只认 `content`：

| 处理方式 | 后果 |
|---------|------|
| 丢弃（原实现） | 思考期间界面**一片空白**，用户以为卡死 |
| 若并入正文 | 用户看到大段"让我想想…不对，应该是…"的自我修正碎碎念，且污染上下文 |

### 根因
`OpenAICompatibleAdapter` 的流式解析只有 `if (delta.content)`，非流式只有 `message.content`，
厂商的推理字段（DeepSeek/千问/智谱用 `reasoning_content`，OpenAI o 系列用 `reasoning`）完全没接。

### 修复（四层打通）
| 层 | 改动 |
|----|------|
| 类型 | `ChatResponse.reasoning`、`ChatChunk.reasoningDelta` |

## 2026-09-18 — 消除远程 HTML 信任面：服务端 README 改取原始 Markdown

### 现象

`githubClient.getReadmeHtml()` 用 `Accept: application/vnd.github.html+json` 取回

|---|---|---|
| Accept | `application/vnd.github.html+json` | **`application/vnd.github.raw`** |
| 方法 | `getReadmeHtml()` | `getReadmeMarkdown()` |
| 返回 | 裸 HTML | **原始 Markdown** |
| 前端 | `sanitizeHtml()` 消毒 | `renderMarkdown()`（与聊天消息同一条路径） |

1. **信任面被消除而非过滤** —— 不存在"远程 HTML 进 DOM"这一步

## 2026-09-18 — P1-4 前端 Markdown 渲染加固：修掉两个 XSS 缺口 + 补上表格/代码高亮

### 现象
审核报告 D9 记录了「Markdown 渲染器可构造属性逃逸」。实际勘察发现问题面更宽：
**3 处渲染点**、**2 类安全缺口**、**1 处样式静默失效**。

### 根因
原自研正则渲染器（`MessageList.tsx`）第一步只转义 `& < >` 而**漏了 `"`**，
后续又把链接的 `$2` 直接拼进 `href="$2"` —— 两个缺口同时成立：

| # | 缺口 | 攻击样例 |
|---|------|---------|
| ① | `"` 未转义 → 属性逃逸 | `[链接](x" onmouseover="alert(1))` 拼出 `<a href="x" onmouseover="...">` |
| ② | **URI 协议完全不过滤** | `[点我](javascript:alert(1))` **点击即执行** |

此外 `PluginsMarket.tsx` 把**GitHub 远程 README 裸 HTML** 直接塞进 `dangerouslySetInnerHTML`，**完全无消毒**；

### 修复

| 路径 | 手段 |
|------|------|
| 本地 Markdown → `renderMarkdown()` | `html:false` 转义原始 HTML + `validateLink` 协议白名单 + 链接统一 `rel="noopener noreferrer"` |
| 远程不可信 HTML → `sanitizeHtml()` | DOMPurify 消毒（README 唯一入口） |

代码高亮按需注册 16 种语言，并补了 `js/ts/sh/py/yml/html` 等 20 组别名（AI 生成的围栏标签很随意）。

### 新增测试

### 踩坑

## 2026-07-02 21:55 — 方案 D 三连 Bug 修复：manifest 缺失 / 路径硬编码 / base 404

### 现象
用户截图：插件市场页面右上角反复弹出"安装失败：插件缺少 manifest.json 文件"提示横幅。手动 `GET C:\Users\ht182\.easyagent\plugins\obsidian-doc-viewer\` 确认目录为空。

### 根因（三层叠加）

#### Bug 1: `extractZip` 把平铺 plugin.zip 误判为 GitHub zipball
**位置**：`PluginMarketService.ts:551-553`  
**问题**：原代码用 `dirs.find(d => d.isDirectory() && ...)` 找第一个子目录，作为 GitHub zipball 的包装层。但我们 CI 打的 `plugin.zip` 是**平铺结构**（`manifest.json` + `plugin.js` + `dist/` 三个顶层项），`dist/` 是第一个也是唯一子目录，被误判为包装层。  
**结果**：只把 `dist/` 内容拷到 pluginDir，`manifest.json`/`plugin.js` 被遗弃在 tmpDir，然后 line 464 `existsSync(manifestPath)` 失败 → 抛"缺少 manifest.json" → line 494 catch 清理 pluginDir → 用户看到的目录是空的。

#### Bug 2: `docViewerDistPath` 硬编码 `obsidian-doc-viewer`
**位置**：`server/src/index.ts:3211`  
**问题**：插件目录名实际是 GitHub 仓库名 `easyagent-plugin-obsidian-doc-viewer`（`pluginIdToName` 取 `id.split('/')[1]`），但 Server 端硬编码 `obsidian-plugin-obsidian-doc-viewer`（即 `easyagent-plugin-obsidian-doc-viewer` 的简写），两个不一致导致 Server 永远找不到 dist。

#### Bug 3: vite `base: '/'` 导致资源 404
**位置**：插件仓库 `vite.config.ts:7`  
**问题**：HTML 里引用 `/assets/index-*.js` 绝对路径，浏览器在 `http://localhost:3456/doc-viewer/` 下解析为 `http://localhost:3456/assets/...`，但 Server 的 `app.use('/doc-viewer', ...)` 只在 `/doc-viewer` 前缀下托管 → 404。

### 修复

| 文件 | 改动 |
|------|------|
| `PluginMarketService.ts` | extractZip 新增 `isFlatLayout` 标记：检查顶层是否有 `manifest.json`/`plugin.js`；asset 查找名 `dist.zip` → `plugin.zip`；CI 打包改为 `manifest.json` + `plugin.js` + `dist/` 三件套 |
| `server/src/index.ts` | docViewerDistPath 改为动态 `readdirSync(pluginsBaseDir)` 扫描，跳过 `.cache`/`.` 前缀目录 |
| `vite.config.ts` | `base: '/'` → `base: '/doc-viewer/'`；server.open 指向 `/doc-viewer/`；README 更新访问地址 |
| `.github/workflows/build.yml` | `zip -r dist.zip dist/` → `zip -r plugin.zip manifest.json plugin.js dist/` |

### 关键教训
1. **`extractZip` 必须区分 zipball 模式 vs 平铺模式**：不要仅凭"第一个子目录"判断，应该用标记文件（manifest.json/package.json）区分。
