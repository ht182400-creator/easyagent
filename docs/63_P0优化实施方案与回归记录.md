## 二、P0-1 安全加固

### 2.1 问题回顾（实测）

`packages/server/src/index.ts` 中 **REST 侧完全没有入站鉴权**：

- `grep -n "Authorization"` 仅命中"调用上游 LLM"处；
- WebSocket 虽有 `EASYAGENT_WS_TOKEN` 校验，但写法是 `if (serverToken && reqToken !== serverToken)`
  —— **不设置该环境变量就等于完全不校验**；
- 服务默认 `HOST = '0.0.0.0'`，且正部署在公网（`82.156.71.231:3456` / `CCCN.fable5.icu`）。

可达攻击面（无需任何凭据）：`POST /api/chat`（白嫖 API Key）、`GET /api/files/browse`（读任意文件）、
`POST /api/sandbox/:id/exec`（执行命令）、`PUT /api/providers/:id/key`（覆盖密钥）、`GET /api/sessions`（读全部对话）。

### 2.2 设计决策（关键取舍）

| 决策                                                | 理由                                                                                             |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **默认监听地址 `0.0.0.0` → `127.0.0.1`**            | 未显式配置时服务根本不暴露。这是单点收益最大的一条，且对本地使用零影响                           |
| **回环地址免鉴权**                                  | Desktop / 本地 Web 走 `127.0.0.1`，不引入任何使用摩擦。安全与体验的边界划在"是否跨主机"          |
| **非回环监听 + 无令牌 = 拒绝启动（fail-fast）**     | 宁可起不来，也不能"忘了配令牌"就悄悄裸奔。需显式 `EASYAGENT_ALLOW_REMOTE_NO_AUTH=1` 才放行       |
| **令牌自动生成并持久化到 `~/.easyagent/api-token`** | 避免"必须手配才能用"，同时保证重启后客户端不必换令牌                                             |
| **WS 与 REST 共用同一令牌体系**                     | 原先两套互不相关、且 WS 的校验可被"不设环境变量"绕过                                             |
| **浏览器用 `?token=` 换取 Cookie**                  | 公网 Web UI 才能用；令牌只出现一次，随后 302 跳转到去掉 token 的干净 URL                         |
| **限流放带宽裕（全局 600/min，高成本 30/min）**     | 目标是挡住扫描与刷钱，不是精细配额；高成本端点单列配额（一次 `/api/chat` 可能触发多次 LLM 调用） |
| **`trustProxy` 必须显式开启**                       | 置于 Caddy/Nginx 之后时 `req.ip` 恒为代理地址，会让"回环免鉴权"与限流同时失真                    |

### 2.3 交付物

| 文件                                                 | 说明                                                                                                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |

| 变量                             | 默认                            | 说明                         |
| -------------------------------- | ------------------------------- | ---------------------------- |
| `HOST`                           | **`127.0.0.1`**（原 `0.0.0.0`） | 公网部署须显式设 `0.0.0.0`   |

### 3.3 附加修复：前端 unhandled rejection

`frontend` 包 **113 个用例全部通过，但 vitest 退出码为 1**：

- 根因：`api.test.ts`「连续失败后应最终拒绝」先推进定时器、后 `await promise`，
  promise 在推进期间就已 rejected 且无人接手 → Node 判定为 unhandled rejection；
- 后果：**CI 变红但报错信息与用例无关，极难排查**；
- 修复：立即挂载 rejection 处理，再推进定时器。

**这是一类值得警惕的失败模式**：用例全绿 ≠ 包健康。因此 `run-tests-log.mjs` 会同时记录
「用例失败数」与「进程退出码」，两者不一致时明确提示。

## 四、P0-3 数据单一真源

### 4.1 问题回顾

测试用例数在 **6 处各自维护**且互不一致：`docs/03`(1273) / `MEMORY.md`(1195) /
`test-case-mapping.json`(1514) / `pipeline-data.json` / `project-progress-data.json` / `CHANGELOG.md`。
项目自身的《测试数据同步约束》要求六处一致，实际六处全不一致。

### 4.2 方案

**真源只有两个**：

| 真源                                   | 生成方式                                   | 含义                         |
| -------------------------------------- | ------------------------------------------ | ---------------------------- |
| `docs/pipeline/test-case-mapping.json` | `scripts/unified-sync.mjs`（扫描测试文件） | **定义用例**（模块映射口径） |
| `docs/pipeline/_vitest-*.json`         | 各包 vitest 运行                           | **实测执行/通过/失败**       |

**门禁**：`scripts/verify-data-consistency.mjs` 校验 ① mapping 自洽 ② KPI 与真源/实测一致
③ 文档声明了当前权威数字。失败即退出码 1，可直接用于 CI。

### 4.3 两个设计取舍（避免门禁变成"狼来了"）

1. **只校验、不修改文件** —— 历史上"post-commit 钩子改写数据文件"导致提交无法收敛，故本脚本绝不写文件。
2. **文档校验"要求存在"而非"禁止其它数字"** —— 文档中还有大量合法数字（各模块用例数、历史版本数），
   一把抓会制造误报。真正的失效模式是"忘记同步权威数字"，故只检查权威数字是否出现。
   （初版实现确实产生了误报，随即修正 —— 见 §五 的"门禁可信度"）

## 五、P0-5 设计令牌 + 附加阻塞性修复

### 5.1 设计令牌（比审核初稿的结论更严重）

审核初稿称"frontend 的 tailwind 引用了不存在的变量"，方向正确但**类名形态写错了**：
实际组件书写的是 `text-text-primary` / `border-border-subtle`（Tailwind 会按"命名空间-键"拼接），
不是我最初以为的 `text-primary`。精确扫描后的完整事实：

| 包         | 实际状况                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `frontend` | 引用了 `--surface-*` / `--text-*` / `--border-*`，但 CSS 里**从未定义**（CSS 用 `--color-*`）→ 15 个令牌类名全部静默失效；且缺 `shell` / `main` 两个键 |
| `web`      | 只定义了 surface 的部分键，**完全没有 text / border 命名空间**，也没有 shell/sidebar/main/overlay → 对应类名根本没被生成                               |
| `desktop`  | 硬编码一整套 zinc 色板（键齐全）→ **只有桌面端显示正常**                                                                                               |

即：同一段组件代码在 Desktop 与 Web 上呈现完全不同的配色，且 Web 端大面积丢色。

### 5.2 修复

| 文件                                     | 改动                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------- |
| `packages/frontend/tailwind.tokens.mjs`  | **新建**。三端共享的令牌单一真源，全部指向 `index.css` 的 `--color-*` 变量      |
| `packages/frontend/src/styles/index.css` | 新增 6 个语义别名（用 `var()` 间接引用，亮暗主题自动跟随）                      |
| `packages/frontend/tailwind.config.js`   | 改为展开共享令牌                                                                |

### 7.4 本轮最关键的一条经验

> **"用例全绿"不等于"包健康"，"管线有数字"不等于"数字可信"。**
> 本轮遇到的三个最危险的问题都属于这一类：
> ① frontend 113 个用例全通过但退出码为 1（unhandled rejection）；
> ② 管线快照显示 30 个 desktop 失败，实际全通过（快照过期 2.5 个月）；
> ③ 6 处文档宣称 100% 通过，实测有 6 个真实失败。
> **对策：任何结论都必须以"当场重跑"为准，并让门禁脚本替人记住这件事。**
