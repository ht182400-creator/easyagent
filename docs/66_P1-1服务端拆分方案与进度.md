## 一、为什么先建"安全网"再动刀

3827 行、93 条路由的纯搬迁式重构，最大的风险不是"改错逻辑"，而是**静默丢路由**：
现有集成测试只覆盖一部分，漏掉的部分不会报错，直到线上 404 才被发现。

因此**第一步不是搬代码，而是建立可证明等价的手段**：

| 安全网                  | 作用                                                                      | 位置                                                    |
| ----------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------- |
| **路由清单快照测试**    | 用 Express 内部注册表枚举全部路由，与基线逐条比对；**丢失与新增都会失败** | `packages/server/src/__tests__/route-inventory.test.ts` |
| **路由枚举工具**        | 把 `app.all()` 展开的 35 个 HTTP 动词归一化为 `ALL`，让清单可读           | `packages/server/src/utils/routeInventory.ts`           |
| **运行时行为验证**      | 单测覆盖不到的**注册顺序**与**路径基准**约束，真实启动发请求验证          | `scripts/verify-server-routes.mjs`                      |
| **TypeScript 类型检查** | 依赖注入漏字段必然编译失败（搬迁时最实用的机械保证）                      | 语言服务器 / IDE                                        |

### 1.1 建立安全网时的两个实测发现

1. **`app.all('/api/*')` 会展开成 35 条记录**。Express 内部把 `route.methods` 填成全部 HTTP 动词
   （`ACL`/`BIND`/`M-SEARCH`…），若不归一化，一条 404 兜底会在清单里占 35 行，淹没真实差异。
2. **基线首跑就修正了两处误判**：① `app.get('*')`（SPA fallback）是合法路径，
   断言"必须以 `/` 开头"过严；② 语言服务器诊断比根 `tsconfig` 更可信 ——
   根 `tsconfig.json` 的 `exclude` 含 `packages`，跑它其实**什么都没检查**（`TS18003: No inputs were found`）。

### 1.2 更新基线的方式

```powershell
$env:UPDATE_ROUTE_INVENTORY='1'; pnpm --filter @easyagent/server test
```

**⚠️ 更新后必须 review 基线文件的 diff** —— 确认每一处增删都是有意为之的接口变更。

## 二、拆分原则

| 原则                         | 说明                                                                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **纯搬迁**                   | 路由路径、方法、处理逻辑、**注册顺序**全部保持不变                                                          |
| **显式依赖注入**             | 每个模块声明自己的 `XxxRoutesDeps`，**不引入"上帝上下文"**（避免一个巨大 `ServerContext` 变成新的耦合中心） |
| **顺序约束显式化**           | 如 `registerStaticRoutes` 必须最后调用，约束写在模块头注释与调用点注释里                                    |
| **`__dirname` 由调用方传入** | 路径基准取决于**构建产物布局**而非源码布局；从源码文件里取会让"拆文件"意外改变路径解析（极难定位）          |

  **全量回归 1729/1729** · tsup 成功 · 语言服务器 0 诊断

**B. 偶发超时根因修复（semantic/map 假失败的系统性解法）**

- **根因链**：`routes/semantic.ts` 的 map/search/references **每次请求都同步全仓扫描**
  （路由层绕过了 core `SemanticTools` 的 60s 缓存）→ 常态 1~3s vs 测试 15s 超时，
  余量仅 5~15 倍 → 收官阶段"tsup 重建 + verify:all（启动真实服务器探针）+ 复验"连环重负载下
  （实测整套 54s vs 常态 30s，全部测试慢 ~1.8 倍），最重的同步操作首先击穿预算。
  **这就是"偶发经常发生"的机制：无缓存的同步重操作 + 紧超时预算 + 收官期负载尖峰**
- **修复**：
  1. 路由层补缓存（`MAP_CACHE_TTL_MS=60s`，key=`workspace|depth|maxFiles`，`refresh=true` 强制重建）
     —— 对生产 UI 同样是真优化（重复请求不再全量重扫）
  2. 两个 map 用例超时 15s → 30s 并注明原因
  3. **2026-09-19 追加（根因侧闭环，共四轮）**：不再只靠"放宽超时"兜底 —— 修正 `extractSymbols` 的
     **O(n²) 行号计算**（一个压缩 bundle 占 96% 耗时）并跳过压缩产物后，全仓冷启 **11s → ~0.5s**；
     新增 **mtime 增量缓存**（热跑 ~36ms，`analyzeFileCached`/`clearAnalysisCache`）与
     **截断可见化**（`stats.totalCandidates`/`stats.truncated`）；再经剖析（瓶颈是磁盘 I/O 占 59%）
     做 **Buffer 直读 + 并发读盘**（`buildSemanticMapAsync`/`getCodebaseOverviewAsync`）→ 冷启 **~0.26s**，
     且**概览端点**从主线程同步阻塞 618ms 降到 213ms。`depth`/`maxFiles` 现可由 query 覆盖
     （map / search / references 一致）。详见 `docs/修复汇总.md` 同日四条
- **教训**：凡是"请求处理器内做同步重扫描"的端点，测试超时预算必须按最坏负载（而非常态）设定；
  单包复验紧跟全量回归/构建跑出的超时，先复跑再定性

**每批的固定流程**：

1. 读该段落，抽 `RoutesDeps`；
2. 写模块 + 替换为注册调用；
3. 跑 `pnpm --filter @easyagent/server test`（路由快照 + 集成测试）；
4. 跑 `pnpm verify:server-routes`；
5. 语言服务器确认 0 诊断；
6. 全量回归后再进入下一批。

**目标**：`index.ts` 最终收缩到 **≤500 行**（仅保留：初始化各管理器 → 组装依赖 → 注册路由 → 返回服务对象）。

| 2   | **根 `tsconfig.json` 不检查 `packages/`** | 其 `exclude` 含 `packages`，跑它得到的是 `TS18003: No inputs were found` —— **看起来"0 错误"其实是空跑**。类型检查应以语言服务器诊断或包级 `tsconfig` 为准 |
| 3   | **`__dirname` 不要在新模块里取**          | 它取决于构建产物布局；拆文件后源码目录层级变了，取值可能随之改变。由调用方传入最安全                                                                       |
| 4   | **注册顺序要用注释显式固定**              | 顺序约束是"看不见的契约"，搬迁时最容易被破坏。已写在模块头 + 调用点两处                                                                                    |
| 5   | **路由快照要双向比对**                    | 只查"丢失"不够，还要查"新增" —— 意外新增（如重复注册）同样是 bug（快照测试另有重复注册断言）                                                               |
