## §3 八视角审核

### 3.1 架构视角

**✅ 做得好的**

1. **分层正确**：接入层（CLI/Web/Desktop/VS Code）→ 展示层（frontend）→ 服务层（server）→ 引擎层（core/langgraph）→ 外部 LLM。依赖方向单向，无环。
2. **双引擎可切换**是真正的架构亮点：`AgentEngine`（ReAct while 循环）与 LangGraph（Think-Act-Observe 图）通过 `bridge/` + `AIEngineFactory` 解耦，三级优先级配置（CLI > env > file > default）。这在同类项目中极少见。
3. **`mountApp()` 共享前端模式**正确解决了历史遗留的"Web/Desktop 两套前端"债务（`docs/09` 曾将此列为🔴紧急问题，现已闭环）。
4. **模型目录四级降级**（远程 → 缓存 → 内置 → 硬编码）设计扎实，容错意识强。

**❌ 问题与根因**

| 问题 | 根因 | 影响 | 建议 |
|------|------|------|------|
| **`server/src/index.ts` 3759 行单体** | 增量开发时"就近加路由"，缺少强制拆分规范 | 任何改动都有回归风险；新贡献者无法上手；IDE 卡顿 | 按域拆 `routes/{chat,sessions,providers,plugins,skills,tools,im,sandbox,knowledge,automations,semantic,files,langgraph,analytics}.ts` + `middleware/` + `services/`，保留 `index.ts` 仅做装配（目标 ≤120 行） |
| **无数据库迁移机制** | 只有 `CREATE TABLE IF NOT EXISTS` + `PRAGMA WAL` | 一旦表结构变更，现有用户数据无法平滑升级 → 只能让用户删库 | 引入 `user_version` + 顺序迁移脚本（SQLite 原生支持，无需 ORM） |
| **REST 无鉴权**（§3.7 详述） | 设计前提是"本机使用" | 公网部署后完全裸奔 | 见 P0-1 |
| **MCP 协议版本停留在 `2024-11-05`** | 实现时未跟进规范 | 无法连接只支持新版规范的 MCP Server；不支持 streamable HTTP 传输 | 升级到最新规范，补 HTTP/SSE 传输 |
| **core 与 langgraph 存在概念重复** | 两个引擎各自实现 tool bridge / memory | 双份维护成本，行为易漂移 | 明确边界：`core` 拥有 Tool 与 Adapter 的**唯一真源**，`langgraph` 只做编排 |

**架构评分：78/100（B+）** — 骨架优秀，但"服务层没有分层"和"数据层没有演化能力"是两处结构性欠账。

### 3.2 流程视角（构建 / 发布 / CI）

**✅ 做得好的**

- `build.bat` 单一入口 + `verify-build.cjs` 17 类 30+ 项预检，把历史踩坑固化成脚本——**这是全项目最有价值的工程实践**。
- CI 拆 9 个 job + `_test.yml` 可复用 workflow + `sync-pipeline` 自动回写管线数据，已经具备正规产品的 CI 形态。
- 发布链路（`release.mjs` + `release.yml` + `publish`）完整，Tag 推送全自动出包。

**❌ 问题与根因**

| 问题 | 根因 | 影响 | 建议 |
|------|------|------|------|
| **6 处测试数字互相矛盾**（§2.1） | 数据是"多处人工 + 脚本混合写入"，没有单一真源 + 校验门禁 | 外部读者第一个看到的数字就是错的，严重损害可信度 | **单一真源**：`test-case-mapping.json` 为唯一权威，其余全部由脚本生成；CI 增加 `verify-data-consistency.mjs` gate，不一致直接 fail |
| **post-commit 钩子自污染工作区** | 钩子每次提交都重算并改写 `docs/pipeline/*.json` | 提交无法收敛，需 `--no-verify` 绕过，长期形成"脏工作区常态化" | 钩子改为**只读校验**（发现不一致则提示），写入动作移到 CI；或钩子写入 `temp/` 由 CI 负责提交 |
| **CI 全程 Windows-only** | 原生模块（better-sqlite3）编译依赖 Windows 工具链 | 无 Linux/macOS 验证；`release.yml` 也不产出 Linux/macOS 安装包，但 `electron-builder` 配置里有 dmg/AppImage（**配置与流水线不一致**） | 增加 `ubuntu-latest` job 跑不含原生模块的包（core/frontend/web/langgraph）；要么补齐多平台 release，要么删掉 dmg/AppImage 配置 |
| **无发布前烟测** | CI 只跑单测，不启动真实 server | 出现过"测试全绿但 EXE 启动失败"类问题（历史陷阱 #20/#21/#23 均属此类） | 增加 `smoke-test` job：构建产物 → 启动 server → `curl /api/health` → 打一次 `/api/chat`（mock provider） |
| **`preinstall` 硬拦 Node ≥24** | better-sqlite3 无 Node 24 预编译包 | 长期成本：用户在 2026 年底基本都用 Node 24+，会成为安装阻力 | 升级 better-sqlite3 到支持 Node 24 的版本（或改 `node:sqlite`，Node 22+ 内置） |

### 3.3 代码视角

**✅ 做得好的**

- `AgentEngine.ts` 457 行，职责单一，状态机（idle/thinking/acting/done/error）清晰，工具输入日志脱敏。
- `ToolRegistry` 接口设计规范（`ITool` 带 `validate`/`requiresConfirm`/`group`），69 个工具、17 分组有序注册。
- `PluginPermission` 默认拒绝 + 四级权限 + shell 允许列表 —— 安全默认值正确。
- `utils/encryption.ts` 用 AES-256-GCM 存储 API Key，**未发现任何硬编码密钥**（专项扫描 0 命中）。

**❌ 问题与根因**

| # | 问题 | 根因 | 影响 | 建议 |
|---|------|------|------|------|
| C1 | **完全没有上下文工程** | `AgentEngine.run` 中 `messages.push` 无上限，仅靠 `maxTurns` 限轮数；无 token 预算、无历史摘要、无工具结果截断 | 长会话必然撞上下文上限（131k 也扛不住 69 个工具的 schema + 长文件）；`dailyTokenLimit` 只是字段，无实际裁剪动作 | 新增 `ContextManager`：① 工具 schema 按模型规模分级（15/30/全量）② 工具结果超 N 字符截断并落盘 ③ 历史超过预算时用便宜模型做滚动摘要 ④ 预算不足时按"系统提示 > 最近 4 轮 > 摘要 > 早期原始消息"优先级丢弃 |

| Agent 编排 | ReAct + LangGraph 双引擎 | Graph/Workflow 化 + Subagent 委派 + 人工审批节点（HITL） | **小**：LangGraph 已在上限；缺 subagent 并行与 HITL 审批 |
| 上下文工程 | ❌ 无 | Token 预算 / 滚动摘要 / 工具结果压缩 / prompt caching / 分层记忆（工作记忆+长期记忆） | **大** ← **最大架构差距** |
| 语义检索 | ❌ 关键词匹配 | 向量检索（`sqlite-vec` / LanceDB 本地化已成主流） | **大** |
| 可观测性 | 本地 pino 日志 + 自建管线仪表板 | OpenTelemetry GenAI 语义约定 + LangSmith/Langfuse 式 trace | **中**：缺 span 级 trace（一次任务中各工具耗时/成败） |
| 沙箱 | Docker 优先，降级本地进程 + 命令白名单 | 容器 + 网络隔离 + 资源配额（cgroup）+ 只读挂载 | **中**：无资源配额 |
| 会话持久化 | SQLite `sessions` + LangGraph `checkpoints` | 同（SQLite/Postgres）+ 迁移机制 | **小**：仅缺迁移 |

### 4.2 为什么"上下文工程"是最大差距（重点）

2026 年的共识是：**Agent 的能力上限由模型决定，但 Agent 的实际表现由上下文工程决定**。同一个模型，上下文喂得好与坏，任务成功率差异可达 2~3 倍。

EasyAgent 当前是**"无预算、无压缩、无分层"**：
- 69 个工具的 JSON schema 无条件全量下发（陷阱 #42 实测占上下文 19~25%）
- 工具结果（可能整个文件内容）直接 push 进 messages，无截断
- 历史消息只增不减，直到撞上限
- 没有 prompt caching（DeepSeek/GLM/Qwen 都支持上下文缓存，可大幅降本提速）

**这解释了为什么项目有 51 个工具却"AI 能力不强"**——不是工具不够，是上下文被工具和原始结果挤爆了。**这是投入产出比最高的改造点**。

## §5 三个点名问题的明确结论

### 5.1 「模型更新到最新、最前沿」——**要更新，但重点在机制不在填数**

**结论：部分更新 + 建立机制。**

1. **立即修（半天）**：
   - OpenAI 预设 `gpt-4o` → 改为当代前沿模型（并把 GPT-4o 标为 Legacy 保留）
   - Ollama 默认 `qwen2.5:7b` → `qwen3.5:9b`
   - 智谱 `glm-5` → `glm-5.2`；通义 `qwen3-max` → Qwen 最新 Max；Kimi → K3；DeepSeek → V4.1 系列

2. **补 provider（1 天）**：新增 **Anthropic（Claude Opus 4.7）** 与 **Google（Gemini 3 / 2.5 Ultra）** 两个预设。理由：EasyAgent 的定位是"集成主流大模型"，把国际前沿模型排除在外会在"能力对比"上先天失分；且**支持 Claude/Gemini 是让用户能对比出国产模型价值的必要条件**。

3. **建机制（1 天）**：
   - `models-catalog.json` 进 CI 校验：schema 校验 + ID 非空 + pricing 非负
   - 每季度自动生成"模型目录差异报告"（新增/下线/改价），PR 化
   - 启动时若默认模型不在 `/v1/models` 返回列表中 → UI 提示 + 一键切换

4. **补能力（1~2 天，与 C2 合并）**：解析 `reasoning_content` / thinking 通道，UI 折叠展示，且**不回灌历史**（避免双重计费）。这是 2026 推理模型的必备支持。

### 5.2 「UI 是否用 three.js」——**明确不建议用于主 UI；仅限 2 个局部场景，且优先选专用库**

**结论：主 UI 不要上 three.js。** 理由（逐条可验证）：

| 判据 | DOM/CSS | three.js（WebGL） |
|------|---------|------------------|
| 文本清晰度 | 原生子像素渲染 | canvas 内文字需自绘/纹理，模糊、无法选中、无法用系统字体变量 |
| 可访问性 | 完整 a11y / 键盘 / 屏幕阅读器 | **零 a11y**，三大框架都无法可访问化 WebGL 内容 |
| 开发效率 | Tailwind + CSS 变量 + 现有令牌体系 | 每处 UI 都是场景图 + 矩阵 + 着色器 |
| 包体积 | ~0 | core + 依赖 ≥ 150KB gzip |
| 本项目适配度 | 现有 16 个页面全是**表单/列表/文本/图表**密集型 | 3D 对其中 90% 的场景是负收益 |

而且本项目**已经走在正确的路上**：图表自绘 SVG（`GraphCanvas.tsx`）、依赖图用 D3（Doc_project）、虚拟滚动用 react-window —— 这些都是编程助手 UI 的正确技术选型。

**唯一值得考虑 WebGL 的 2 处局部场景**：

1. **知识图谱 / 代码依赖图 > 2000 节点**
   当前自绘 SVG 在千级节点会掉帧。但**不要用裸 three.js**——用 `sigma.js`（WebGL 图渲染，专为此场景）或 `cosmograph`；若必须 three.js 生态，用 `react-force-graph`（3D 力导向，封装好）。
   **前置条件**：先验证真实数据规模是否到千级。若典型场景是 200~500 节点，**SVG + 视口裁剪就够，不要引入 WebGL**。

2. **品牌化的"Agent 执行 3D 拓扑"演示页**（可选炫技）
   若想做一个有传播力的可视化（如 LangGraph 节点的 3D 编排动画），用 `@react-three/fiber` + `drei`。但必须：① 独立路由、懒加载 ② 提供"降级为 2D SVG"开关 ③ 不进入主流程。

**如果非要在 UI 上"现代化"，优先级远高于 three.js 的是**：
`monaco-editor`（代码/diff，U3）> `shiki`（高亮，U2）> `markdown-it + remark-gfm`（表格，U2）> `xterm.js`（终端）> 图表用 `visx`/`recharts`。
**这五项的体验收益是 three.js 的 10 倍以上。**

### 5.3 「有必要也可以重构」——**要重构，但只重构 3 处；明确不要动的 4 处**

**必须重构（ROI 由高到低）**

| # | 重构项 | 为什么必须 | 目标 | 工作量 | 风险控制 |
|---|--------|-----------|------|:------:|---------|
| R1 | **抽出 `ContextManager`**（`core/src/agent/context/`） | 上下文工程缺失是最大能力短板（§4.2） | 工具 schema 分级 + 结果截断 + 滚动摘要 + token 预算 | 3d | 特性开关 `EASYAGENT_CONTEXT_V2=1`，A/B 对比同一任务的成功率与 token 消耗；保留旧路径 1 个版本 |
| R2 | **`server/src/index.ts` 拆分** | 3759 行单体，任何改动都是高风险 | `routes/` 14 个域文件 + `middleware/` + `services/`，`index.ts` ≤120 行 | 3d | **纯搬迁重构**，不改逻辑；每拆一个域跑一次 `pnpm test:server` + `curl` 冒烟；用 git 历史保留可回溯 |
| R3 | **知识库接真向量检索** | 当前是 grep，与宣传不符（C3） | `sqlite-vec` + embedding（provider 端点或本地 `bge-m3`） | 2d | 保留关键词检索作为 fallback；embedding 不可用时降级并提示 |

**建议重构（次优先）**

- R4：前端 9 个巨型页面拆分（5d）—— 只在需要改这些页面时顺手拆，不要专门开一个重构 sprint
- R5：`docs/pipeline/index.html` 拆分（1d）—— 2201 行单文件，拆为 `index.html` + `js/{app,charts,panels}.js` + `css/`
- R6：删除死代码（0.5d）—— `components/Layout.tsx`、`ContentRouter.tsx`、30 个孤儿测试、`src/plugins/PluginWorkerEntry.js` 残留（若有）

**明确不要动（避免"半途而废的重构导致版本幽灵"）**

| 不要动 | 理由 |
|--------|------|
| ❌ 不要重写 monorepo 结构 / 换包管理器 | 现有分层正确，pnpm workspace 已踩平所有坑；重写要从头再踩一遍（陷阱 #6/#19/#38/#39） |
| ❌ 不要移除 LangGraph 双引擎 | 这是真差异化；只需统一二者共用的"预算/上下文/工具"抽象 |
| ❌ 不要引入微服务 / 消息队列 / Postgres | 单机单进程是当前正确规模；引入即运维成本爆炸，收益为负 |
| ❌ 不要把 `core/src` 的 `.ts`+`.js` 共存改成 `.ts`-only（当前） | 这会引发 vitest/tsup/electron-builder 的连锁改动（陷阱 #10/#31）。**列为中期事项**，需独立评估 |
| ❌ 不要在此时引入组件库（antd/shadcn） | 现有自研 + 令牌体系已成型，换库等于重写 16 个页面 |

## §8 结论

### 8.1 三句话总结

1. **工程底子超出个人项目的上限** —— 12 包 monorepo、双引擎、9 job CI、17 类构建预检脚本、62 份文档、管线自动聚合，这些放在商业团队里也是及格以上的水平。`verify-build.cjs` 把每条踩过的坑变成自动检查，是**这个项目最值得被其他项目抄走的资产**。
2. **但"自我认知"已经失真** —— 文档宣称 100%/1195 通过，实测 98%/1260 已执行/31 失败；测试数字 6 处互相矛盾；3759 行的服务端违反自己定的 500 行规则 7.5 倍。**当一个工程体系开始相信自己的报告而不校验报告，它就从"工程成熟"退化为"文档繁荣"。**
3. **能力层面有一处硬缺口，安全层面有一个硬伤** —— 上下文工程完全空缺（最大的能力短板，也是最高 ROI 的改造点）；公网 REST 无鉴权（必须今天就修）。

### 8.2 如果只做三件事

| 顺序 | 事项 | 理由 |
|:---:|------|------|
| 1 | **给 REST 加鉴权** | 唯一"不做就可能造成实际损失"的项 |
| 2 | **让数字变可信**（清孤儿测试 + 一致性门禁） | 修复“自我认知失真”——它是所有后续决策的前提 |
| 3 | **抽出 `ContextManager`** | 唯一能改变"AI 到底好不好用"的工程项 |

### 8.3 关于 three.js 的最终回答

> **不要用。** 主 UI 是文本/表单密集型，DOM+CSS 在清晰度、可访问性、开发效率、包体上全面胜出；本项目已有的 SVG + D3 + react-window 选型是正确的。若想提升观感与体验，钱应该花在 **monaco（代码/diff）+ shiki（高亮）+ markdown-it（表格）+ xterm（终端）** 上。只有当**知识图谱超过 2000 个节点**且实测 SVG 掉帧时，才考虑 `sigma.js`（不是裸 three.js），并保留 SVG 降级路径。

### 8.4 关于"是否重构"的最终回答

> **重构 3 处（ContextManager / server 拆包 / 知识库向量化），不要碰 5 处（monorepo 结构、双引擎、技术栈代际大版本、组件库、core 的 ts+js 共存）。** 现有架构骨架是正确的，问题集中在"巨型文件"与"能力空缺"，属于**外科手术式重构**，不是推倒重建。
